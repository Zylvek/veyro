### Инфляционный баг — точный механизм (draft-постмортем, master)

- Дерево note commitments при отсутствии правой ветви подставляло КОПИЮ
  левой: `H(left, left)`. Спенд-пруф аутентифицирует note против
  публичного корня, а позиция остаётся приватной в пруфе; на «скопированной»
  ветви замена бита позиции не меняет корень.
- Позиция напрямую входит в nullifier:
  `rho = cm + NULLIFIER_POSITION_GENERATOR * position`,
  `nullifier = blake2s(nk || rho)`. Та же note, доказанная на «алиасной»
  позиции, даёт ДРУГОЙ nullifier; проверка повторных нуллификаторов
  второй расход не распознаёт; обычная check-балансировки ценностей тоже
  не спасает (повторённый вход под новым nullifier).
- Ограничение атаки: нужен доступ к spending authority и содержимому note —
  тратить ЧУЖИЕ note нельзя; нельзя и «украсть» чужие балансы. Возможна
  инфляция: владелец note многократно тратит СВОЮ note.
- Circuit не привязывает приватную позицию к публичному размеру дерева —
  это сохраняется и после патча (патч чинит построение дерева, а не
  circuit; защита теперь держится на binding позиции корнем).
- Патч #5762: вместо копии ветви — фиксированное пустое значение.
  **Меняет консенсус-корни** → несовместим с существующей историей
  mainnet И testnet; genesis-подобные определения НЕ мигрированы;
  годится только для НОВОЙ цепи с новым генезисом. Нет activation height,
  dual-root verifier, legacy proof migration, плана учёта истории.
  Genesis перегенерирован только для devnet (тест-фикстуры).
- Последствия для владельца средств: ключи/аккаунт не страдают, средства
  доступны; отправка технически работает; НО гарантия стоимости утрачена
  (любой может инфлировать собственные note), поддерживаемого пути
  миграции на исправленную цепь НЕ существует, wIRON на Base не
  обеспечен (фонд сам предупредил), биржевые рейлы (депозиты/выводы)
  закрываются.

## Криптография и ключи

- **Формат адреса:** 64 hex-символа (transmission key pk = «public
  address»). Bech32 для публичных адресов НЕ внедрялся: issue #3030
  закрыт через PR #3213, но #3213 реализовал bech32 только для
  экспорта/импорта аккаунтов. Префиксы «iron1/ore1» никогда не
  существовали.
- **Формат публичного ключа:** transmission key (pk) — производная от
  spending-ключей; модель Sapling-подобная (whitepaper).
- **Формат приватного ключа:** spending key (sk) — 256-битный случайный
  ключ; экспорт AccountFormat «SpendingKey» — hex-строка. Экспорт
  аккаунта: bech32-строка с префиксом `ifaccount` (текущие доки; ранее —
  `ironfishaccount…`), JSON, Base64Json.
- **Модель ключей (whitepaper, проверено):** sk → ask/ak (трата),
  nsk/nk (nullifier), ovk (исходящие), ivk (входящие), pk (адрес).
  Формулы: ask = blake2b(sk‖0, «Iron Fish Money », 512 бит) mod r;
  ak = ask·SPENDING_KEY_GENERATOR; nsk = blake2b(sk‖1, …) mod r
  (кривая Jubjub).
- **Мнемонический стандарт:** 24 слова, кодирующие сам spending key
  (RPC-доки: «The private key encoded as 24 word BIP39 mnemonic phrase»).
  Это кодировка ключа, а не BIP39-деривация: фраза = полный доступ.
- **Watch-only:** view key полный (входящие и исходящие) —
  `ironfish wallet:export --viewonly`; view-only не может тратить.
  Поддержано офлайн-подписание (raw transaction + постинг spending-нодой).
- **Алгоритм подписи:** Jubjub/RedJubjub + zk-доказательства
  (Sapling-производная модель). Ledger-приложение существовало (аккаунты,
  multisig/DKG, tраты; статус сегодня не проверялся — НЕ ПОДТВЕРЖДЕНО).

## Транзакции

- **Структура:** notes + nullifiers, зашифрованные суммы
  (Sapling-подобная модель); mints/burns для активов и мостов
  (spends − outputs = fee − mints + burns, whitepaper).
- **Критический баг (в проде с 2023, код 2019):** aliasing позиций в
  Merkle-дереве (`H(left, left)` вместо пустого маркера) → одна и та же
  note может быть потрачена владельцем многократно с разными nullifier;
  ЧУЖИЕ note тратить нельзя. Патч несовместим с живой цепью.
- **Расчёт комиссии:** модель НЕ ЗАФИКСИРОВАНА в рамках исследования.
- **Блокировки/имматурность:** НЕ ЗАФИКСИРОВАНО.
- **Модель баланса:** notes (shielded, account-based).
- **Особые поля:** memo (`ironfish wallet:send --memo`; пример
  майнинг-адрес+memo у Kryptex для Gate.io/KuCoin).

- **Публичные RPC:** поддерживаемых нет; живой публичный read-only

## Безопасность и ограничения

- **Известные ограничения:** consensus-level inflation bug в проде с
  2023 (код 2019); патч требует нового генезиса; существующие цепи
  (mainnet/testnet) в текущем виде невосстановимы; maintainer'ов нет;
  historical attribution (кто/сколько инфлировал native) — открыт.
- **Риски безопасности:** любой нативный IRON — актив без гарантий
  обеспечения инфляции; wIRON (Base) не обеспечен и не покупается; мост
  выключен; биржевые депозиты/выводы приостановлены (MEXC); пулы
  делистятся (Kryptex 10.11, HeroMiners 11.11); тренд hashrate — вниз.
- **Блокеры:** интеграция нецелесообразна: (1) активный непропатченный
  consensus-эксплойт; (2) отсутствие maintainer'ов; (3) затухающая
  инфраструктура и ликвидность.

  выключен, биржи и пулы закрывают сервисы. Хранение и отправка
  небезопасны/экономически неустойчивы — интеграция нецелесообразна.»
  Формулировки вида «сеть остановлена/мертва, остановка 30.10.2026» —
  НЕВЕРНЫ и не должны использоваться.
- **Главный риск (если хранить):** неизлечимая инфляция consensus-уровня
  (любой участник может эмитировать фиктивные value-выходы) + отсутствие
  пути на исправленную цепь + закрытие биржевых/мостовидных рейлов
  вывода стоимости.
- **Условия пересмотра статуса:** (1) официальный либо координированный
  community-рестарт на новой цепи с патченным генезисом+аудитором и
  РАБОТАЮЩЕЙ миграцией/claim-аирдропом балансов; (2) появление
  поддерживаемых мейнтейнеров и восстанавливающейся инфраструктуры
  (bootstrap/seed, explorer с живыми данными, публичный RPC, ликвидные
  рынки без ограничений рейлов); (3) завершённый forensic-отчёт об
  объёме нанесённой инфляции в native-цепи.
