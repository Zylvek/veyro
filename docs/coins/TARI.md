## Криптография и ключи

- **Формат адреса (OotleAddress):** **Bech32m** строка; human-readable prefix определяет сеть: mainnet `otl_`, stagenet `otl_stg_`, nextnet `otl_nxt_`, esmeralda `otl_esm_`, igor `otl_igr_`, localnet `otl_loc_`. Состав (32+32 байта в теле): **account public key** (spend, Ristretto255, 32B) + **view public key** (32B) + опциональный **destination tag** (1–64 байта). Адрес без тега на mainnet = **114 символов** (пример из гайда: `otl_17mufuvtwdwjlqhjj2rwaffwna5uae5pce7qje34p2jmwcz236f0sd7pjcd8eeytpr4lqk0htsk3e740g7gre3t3s4h47cwz7swvrw3secjh6l`). Чексумма — стандартная Bech32m. Уникальные deposit-адреса строятся приклеиванием тега и перекодированием (Rust `base_address.with_destination_tag(tag)`; TS `encodeOotleAddress`). **Интерактивных/односторонних «режимов» нет** (в отличие от L1), проверка feature-байта не нужна. После `from_str` обязательно проверять `OotleAddress::validate()` (валидность Ristretto-точек).
- **Внутренние адреса субстейтов:** каноническая форма `<prefix>_<body>`: `resource_…`, `component_…`, `utxo_…`, `template_…` (release 0.50.1/0.53: парсинг только канонический; utxo-адрес = `utxo_<resource hex>_<id>`).
- **Формат публичного ключа:** Ristretto255 (tari-crypto, семейство curve25519-dalek). У каждого OotleAddress **двa ключа**: account (spend) + view. Стилт-адреса: для каждого UTXO одноразовый ключ `P = c·G + K`, где `c = H(r·V)` (DH между sender nonce r и view ключом получателя), spend-ключ `p = c + k`; эфемерная nonce `R = r·G` публикуется для сканирования. KDF-домен примешивает Network (кросс-сетка не переносится) — `crates/wallet/crypto/src/kdfs.rs`.
- **Формат приватного ключа:** сид **CipherSeed** (нативная схема Tari из `tari_common_types::seeds::{cipher_seed::CipherSeed, seed_words::SeedWords}` — тот же стандарт, что у L1 LibWallet) — **НЕ BIP39, НЕ BIP32/BIP44**. Экспорт read-only: `view_only_private_key` (view секретный ключ, hex) + `account_public_key` (`accounts.export_view_key`); резервная копия — **только seed-слова** (SQLite-база не содержит расшифрованный сид).
- **Схема деривации ключей:** нативная Tari: CipherSeed → детерминированный вывод ключей аккаунта и view (Golden-векторы в `crates/ootle_sdk_core/fixtures/keys/{account_from_seed,view_from_seed}.json` — кросс-языковая воспроизводимость контракт). Для построения стелс-транзакций — «seed expansion» v1: домен **`ootle.sdk.entropy.v1`**, Blake2b-512 над `domain ‖ label ‖ seed ‖ index(u64 LE)` → скаляр Ristretto (метки `mask`, `sender-nonce`, `aead-nonce`, `elgamal-nonce`, `zk-*`); подписи НЕ наследуются от seed (свежие случайные nonce). Claim-ключи (для сжигания XTM) выводятся из того же сида кошелька. **SLIP-44 coin type: ОТСУТСТВУЕТ** — полный файл slip-0044.md проверен 11.11.2026, записей Tari/TARI/XTR/XTM/Minotari нет; BIP-совместимости нет.
- **Мнемонический стандарт:** seed-словарь **CipherSeed** (родной Tari; на L1 — 24 слова из предопределённого списка; для validator identity в 0.51.0 явно 24-словная схема `--seed-words`; для кошелька Ootle `--seed-words` восстанавливает `create-account`/`seed-words` экспорт). Точное количество слов для Ootle-кошелька в доках не названо (наследуется от Tari cipher seed — `НЕ ПОДТВЕРЖДЕНО` отдельно), но это **та же не-BIP39 схема**, что в XTM.md: чужой BIP39-кошелёк фразу не примет.
- **Алгоритм подписи:** **Schnorr на Ristretto255** (ownership proof сжигания, balance proof signatures, spend authorization), Bulletproofs+ (64-bit, агрегация до 16) для range proofs, Pedersen commitments `C = mask·G + v·H` (Extended factory), ElGamal viewable balances, шифрование payload **XChaCha20-Poly1305** (value/mask/memo 0–255B), внутренний хэш — **Blake2b с доменной сепарацией** (доступны SHA-256/512, Keccak256 из шаблонов); spend-условия — Merkle-ное MAST дерево. Криптобиблиотека — `tari-crypto` (BSD-3).
- **Совместимость восстановления из фразы:** только внутри экосистемы Tari (Ootle-кошельки / SDK с cipher seed). Сторонние BIP39/BIP44-кошельки несовместимы. Дисклеймер гайда: перед переносом реальных средств на адреса, полученные до объявления запуска, сверить адреса/деривацию с mainnet release notes (возможны изменения плейсхолдеров).

## Транзакции

- **Структура транзакции:** JSON-RPC `transactions.submit` / `submit_manifest`; тело V1: `network` байт (0 mainnet / 38 esmeralda), `fee_instructions` (сначала платёж комиссии), `instructions` (CallMethod/CallFunction/**ClaimBurn**/stealth transfer и др.), validity-окно `max_epoch` (по умолчанию ~1 час вперёд; истёкшая по эпохе — аборт). Модель исполнения — транзакция → инструкции → diff субстейтов; статусы нативные см. ниже.
- **TARI — stealth-ресурс:** суммы и владельцы скрыты; UTXO со стилт-адресами; комиссии платятся **revealed-выходом** (сумма комиссии публична by design); change и суммы — конфиденциальны. Стилт-переводы дороже публичных, fee растёт с числом inputs/outputs.
- **Расчёт комиссии:** детерминированный метринг за работу (weight per instruction, аргументы метрятся при декодировании, таблицы 24 пункта и т.д.); сжигание **доли комиссии** (ExhaustBurnRate bps, по эпохам): **mainnet genesis 10 000 bps (100%)** — live подтверждено (~99,9%), тестнет 500 bps по доке / по live-полю esmeralda `target_burn_rate_bps` = 10000 на 11.11.2026 (расхождение с докой — учитывать при тестах). Валидатор получает остаток (на mainnet = 0). Для стил-трансфера fee уточняется **dry-run** (`transactions.get` → `final_fee`); в `max_fee` для stealth_transfer платится фактически (surplus НЕ возвращается — оверпей).
- **Блокировки/имматурность:** нет блокчейн-подтверждений (BFT-финальность мгновенна); вместо этого validity-окно по эпохам и статусы результата. Единственная внемодульная задержка — **окно подтверждения сжигания L1** (см. ниже).
- **Модель баланса:** stealth UTXO (конфиденциальные) + счета акканта-компонентов (vaults) для публичных/конфиденциальных ресурсов; балансы watch-only строятся из скана UTXO по view-ключу.
- **Особые поля:** **destination tag** (1–64B, вшит в адрес и копируется в зашифрованный memo отправителем по умолчанию; НЕ гарантируется —sender может перезаписать/убрать; memo-формы: `DestinationTagAndBytes`, `SenderAddress`, `Message`-текст) — референс платежа; `sender_address` в memo — информационный, НЕ идентификация отправителя. Комиссионный intent «fee» может сам исполнить перевод (микросуммы) → статус **OnlyFeeAccepted** (payment возможно прошёл — только ручной разбор).
- **Статусы результата (wallet):** `New` / `Pending` / `Accepted` (финал OK) / `OnlyFeeAccepted` (финал, неоднозначный — manual review) / `Rejected` (консенсус, fee не берётся) / `InvalidTransaction` (мемпул, fee нет). Indexer: `GET /transactions/{id}/result` → `Finalized{Commit|Abort}` / `Rejected`. Resubmit только при финальном неуспехе.
- **L1↔L2 (сжигание XTM → TARI):** одна дорога: burn на L1 (output со burn-флагом + claim_public_key) → **ClaimBurn** на L2 с `MinotariBurnClaimProof` (commitment + Schnorr ownership proof + Merkle proof против L1 блока). Пегина 1:1 (1 µXTM = 1 µT TARI) минус fee заявки. Двойной клейм блокируется tombstone'ом от commitment. **Пег-аута НЕТ** (Turbine Model — осознанный one-way; submarine swaps O-0310 только Proposed). Механика сейчас: `minotari_console_wallet` Burn-таб / gRPC `Wallet/CreateBurnTransaction` (порт L1-кошелька 18143 esmeralda, **18103 mainnet**), proof-файл в `~/.tari|APPDATA/tari/<network>/burn_proofs/`, автоклейм демоном; подтверждение L1: ~<1 ч (esmeralda) / **~сутки (mainnet)**. Ошибка клейм-ключа или непустой sidechain key = средства потеряны навсегда.

## Доступ к сети

- **Wallet JSON-RPC (основной API):** `tari_ootle_walletd`; JSON-RPC 2.0 POST `http://127.0.0.1:5100/json_rpc` (default `JRPC_LISTEN_ON`; в старой skill-доке 12008), web UI на том же порту; auth: WebAuthn (default) + **API-ключи** `tw_…` со скоупами (`accounts:read`, `stealth_utxos:read`, `transactions:read`, `transfer:create:<addr>`, `burn_proofs:read`…), JWT-сессии; `indexer_trust="verify"` — проверка поступающих proof'ов (для депозитных кошельков выставлять явно; default = "trust"). Сид в OS keyring (Windows Credential Manager/keychain/Secret Service) или override-пароль. Ключевые методы: `accounts.list|get|get_default|get_balances|get_balance_changes|create|import_view_only|export_view_key|stealth_transfer|claim_burn`, `stealth_utxos.list`, `transactions.submit|submit_manifest|wait_result|get_result|list`, `burn_proofs.list`, `substates.get`, `templates.get`, `nfts.list`, `auth.*`. Dry-run поддерживается (`dry_run:true`).
- **Indexer REST/SSE (индексирующая нода):** `tari_indexer` (Linux/macOS only; Docker `ghcr.io/tari-project/ootle`, linux/amd64), REST `:18300` (+swagger-ui, prometheus `:18302/_metrics`, web UI `:15000`). Проверенный полный список эндпоинтов (11.11.2026, OpenAPI): `/committees`, `/epoch-checkpoints[+latest,/shard-groups]`, `/epoch-manager/stats`, `/events` (SSE), `/identity`, `/info`, `/network[|connections|economics|stats]`, `/resources/tari`, `/resources/{resource_address}`, `/substates/fetch` и `/substates/{id}`, `/templates/catalogue`, `/templates/{address}`, `/transaction-receipts[+/{addr}]`, `/transactions`, `/transactions/dry-run`, `/transactions/events/stream`, `/transactions/recent`, `/transactions/{id}`, `/transactions/{id}/result`, `/utxos/fetch`, `/utxos/stream`, `/validators`, `/wait-until-ready`; health/ready/info. Indexer — единственный путь кошельков к сети (submit через indexer); публичные: mainnet `indexer-a/b.ootle.tari.com`, esmeralda `esme-indexer-a/b.ootle.tari.com` (оба отмечены в доке как «placeholder до запуска»).
- **Validator node RPC:** libp2p gossip `transactions`/`consensus` (TCP+Noise+yamux, QUIC, relay); публичный VN в README (Igor) `:12006`; для кошелька участвовать не требуется.
- **Лёгкий клиент:** **есть официально**: (а) watch-only через view key (`accounts.import_view_only` + скан UTXO indexer'а); (б) SDK-скан: `ootle-rs: IndexerProvider::watch_stealth_utxos`, `ootle_sdk_core::stealth::scan_stealth_output` — сборка баланса/истории без своего узла; при этом wallet/SDK **проверяют cryptо-доказательства** (proof'ы субстейтов/QC от indexer при `indexer_trust=verify`, валидация spend-ключей при скане).
- **Узел:** validator node (консенсус+TVM+epoch oracle→L1 gRPC), indexer, walletd; требования для indexer: Linux 4 ядер/8–16ГБ RAM/200+ГБ NVMe (production); validator requirements — отдельная страница доки (не интегрируется в кошелёк VEYRO). Ootle **не использует Tor** (в отличие от L1).
- **Explorer:** полноценного публичного block explorer UI для Ootle на 11.11.2026 НЕ обнаружено (tari.com ссылает explore.tari.com — это L1; `https://explorer.ootle.tari.com` — пустой ответ; lobby.tari.com — контест-хаб). Функционально роль «проводника» играет REST индексера: `/transactions/recent`, `/transactions/{id}/result`, `/resources/{addr}`, `/network/economics` — ссылки для истории транзакций строить на них (со своими индексерами) или на `https://ootle.tari.com` (доки). Встроенный web UI индексера (порт 15000) — локальный монитор.
- **Приватность доступа:** подключение к чужому индексеру раскрывает ему ваши запросы (какие UTXO/аккаунты смотрите); wallet может верифицировать ответы (`indexer_trust=verify`) — приватность метаданных лучше, чем у RPC-ноды с trust, но не анонимна; сабмит транзакций идёт через тот же indexer.

## Безопасность и ограничения

- **Известные ограничения:** one-way мост (нет вывода TARI→XTM; вернуть ликвидность можно только продажей TARI на вторичном рынке, которого ещё нет); 100% fee burn на mainnet (валидаторы пока без дохода — устойчивость модели под вопросом); транзакции живут ~1 час (validity epochs); stealth transfer fee не рефандится; CLI не умеет стилт-переводы; индексер только Linux/macOS; Tor не поддерживается.
- **Риски безопасности:**
  - **Малый и однородный валидатор-сет на старте:** 7 валидаторов в бандлед set, live `/validators` показывает единый `fee_claim_public_key` у всех — фактически один оператор держит BFT-кворум. Это НЕ кастодиальность ключей (ключи пользователя локальны), но **траст уровня протокола**: кворум валидаторов может финализировать состояние (HotStuff ≥⅔+1). Риск «центральный оператор L2 на старте» — главный для честной некастодиальной оценки.
  - **Официальные «placeholder»-дисклеймеры:** адреса/деривация/индексеры/fee до финального launch announcement могли и могут измениться; релизы Pre-release, ежедневные breaking-обновления, SDK и сеть апгрейдятся «вместе».
  - **indexer_trust** default = "trust": без явного "verify" кошелёк верит индексеру → подделка балансов/депозитов возможна со стороны скомпрометированного/злонамеренного индексера. В VEYRO включать verify.
  - **ClaimBurn неопровратим:** неверный claim public key / непустой sidechain key = безвозвратная потеря XTM; автоклейм зависит от совпадения путей proof-каталогов; окно подтверждения на mainnet ~сутки.
  - **Приватность leaks (официальный threat model):** комиссии публичны; графики транзакций публичны; подпись публичным ключом метода линкует личность; `stealth_utxos.list` не содержит времени/txid (аудит — через `get_balance_changes`); sender_address в memo ненадёжен.
  - **Символ/тикер-путаница:** XTR (истор.) vs TARI vs tTARI vs XTM — обязательный UI-дискриминатор активов (ресурс-ID констант в коде).
- **Блокеры (для VEYRO сегодня):** (1) неопределённость «запущен ли mainnet официально» — гайд говорит placeholders; (2) не-BIP39 сид — собственный wallet-слой обязателен; (3) нет Dart SDK; (4) нет публичного explorer-UI; (5) end-user кошельков нет — пользователь VEYRO станет одним из первых, с риском UX/поведенческих изменений сети.

## Вывод для матрицы поддержки

**Актив идентифицирован уверенно, но сетевой статус — «переходный» (мягкий запуск 11.11.2026).** Текущие факты: chain mainnet живёт (индексеры, чекпоинты, экономика, ClaimBurn'ы — проверено 11.11.2026), тестнет Esmeralda стабилен (4408+ транзакций), SDK свежие (вчерашние/сегодняшние билды), но официальная позиция Tari — «mainnet не запущен, значения-плейсхолдеры», пользовательских кошельков нет, биржевых списков нет, монета в трекерах отсутствует.

Рекомендуемый статус матрицы: **«Research required → Watch-only позже; при немедленной потребности — не включать в пользовательскую матрицу до финального launch-анонса Tari»**. Обоснование:
- **Не Receive прямо сейчас:** mainnet-адреса официально названы возможными плейсхолдерами (дисклеймер гайда) — выдавать пользователям адреса до релиз-ноутов запуска нельзя;
- **Техническая досягаемость подтверждена:** Rust SDK (BSD-3) + walletd JSON-RPC + REST/SSE индексера позволяют реализовать Receive/Send/Watch позже без своих серверов (индексер — сторонняя официальная инфраструктура, доказательства проверяемы);
- **Не майнится**, создавание только сжиганием XTM 1:1 — для майнинговой матрицы непригоден (в отличие от XTM).

Чек-лист VEYRO (ближайшие шаги, если решим поддерживать):
1. Дождаться официального «launch»-анонса Tari (счётчики burn'ов на tari.com >0; снятие placeholder-дисклеймеров в exchange-гайде).
2. Spike: `ootle-rs`/`tari_ootle_address` вендорить в VEYRO (BSD-3 совместимо), адреса/валидация/скан по golden vectors.
3. Интеграция через официальный публичный индексер + `indexer_trust=verify`-эквивалент в клиенте (проверка proof'ов обязательна).
4. Сид: реализовать/вендорить Tari CipherSeed (совместимость с L1-сида XTM — `НЕ ПОДТВЕРЖДЕНО` для Ootle-аккаунтов; проверять).
5. UX: жёсткое разделение активов XTM ≠ TARI (≠XTR истор.); показать one-way мост и 1:1; предупреждение про destination tag.
6. Мониторинг: релизы (Pre-release!), breaking-ноты 0.5x, изменение epoch-оракула, расширение валидатор-сета, появление эксплорера и end-user кошельков.
